# Story 5.1: AI Mini-Quiz Generator & Grading

Status: ready-for-dev

## Story

As an Employee,
I want to take mini-quizzes generated by the AI on a specific skill or course,
so that I can validate my knowledge quickly without leaving the chat workflow.

## Acceptance Criteria

1. **Given** an employee asks the assistant to test a specific skill or course in chat
2. **When** the backend/orchestration flow determines that a quiz is needed for `learning_training_agent`
3. **Then** the system must obtain quiz content through the training domain and expose it via `POST /internal/tools/training/quiz/generate` using the internal scoped token flow
4. **And** the assistant turn delivered to the frontend must include readable assistant text plus one compact structured `uiPayload` of type `quiz` over the existing SSE chat contract
5. **Given** the employee answers that inline quiz card
6. **When** the frontend submits the answers through an authenticated backend API
7. **Then** the backend must grade the submission from stored quiz question answer keys, persist a `quiz_attempts` row for the authenticated user only, and return a result payload without exposing raw answer keys to the client
8. **And** the chat UI must render the quiz result inline in the same conversation without a full page reload
9. **And** reopening conversation history must still hydrate the quiz card and result state correctly from persisted message metadata
10. **And** all quiz generation, submission, and result retrieval paths must preserve traceability, audit logging, ownership checks, and graceful fallback to plain text if the structured payload is missing or malformed

## Dev Notes

### Story Intent

Story 5.1 is the first implementation slice of Epic 5. The goal is not just to show static quiz data, but to deliver an end-to-end quiz loop inside chat: secure generation, inline answering, grading, persistence, and result rendering that still respects the system's zero-trust boundaries.

### Epic and Product Context

- Epic 5 introduces the `learning_training_agent` growth area for personalized learning and mini-quizzes.
- The system-level architecture already reserves the training tool surface for `generate_quiz`, `submit_quiz`, and `get_quiz_result`.
- The acceptance target is a chat-native learning experience, not a separate exam page or a direct database utility.

### Current Codebase Intelligence

- `be/src/modules/training/training.module.ts` exists but is still empty, so this story must establish the first real backend training implementation surface.
- `be/src/modules/chat/chat.service.ts` still emits a mock assistant stream, so the quiz experience needs a narrow structured payload contract rather than assuming a finished domain-aware OpenClaw integration already exists.
- `be/src/modules/onboarding/onboarding.internal.controller.ts` and `be/src/modules/onboarding/onboarding.service.ts` are the best live examples of how internal tool endpoints should be structured in this repo.
- `be/src/modules/auth/guards/internal-agent.guard.ts` already enforces token validation, header cross-checks, scope checks, and ownership protections. Reuse it.
- `be/src/modules/tool-gateway/tool-call-logging.interceptor.ts` and related tool-gateway services already implement the append-only audit path for internal tool calls. Reuse that path instead of inventing a quiz-specific logger.
- `fe/src/pages/ChatDashboardPage.jsx` already renders structured assistant cards for checklist and support contacts inline inside chat.
- `fe/src/services/chatService.js` already normalizes explicit/persisted `uiPayload` data plus embedded payload markers, but it currently knows only checklist and support-contact shapes.
- `be/src/modules/chat/conversation.service.ts` can save message metadata today, but `getMessagesForUser()` currently returns only `id`, `sender_type`, `content`, and `created_at`; this is not enough for structured quiz history rehydration and must be corrected if quiz cards need to survive reload.

### Architecture Compliance

- Backend remains the security boundary for auth, RBAC, scoped internal tokens, tool routing, and audit.
- Frontend must continue using authenticated external backend APIs only.
- OpenClaw remains an AI worker and must not query PostgreSQL directly.
- Internal quiz routes must live under `/internal/tools/training/*`, while frontend-facing quiz submission/result routes must stay in the external API namespace.
- Do not mix external and internal auth models in the same controller surface.

### Project Structure Notes

- The architecture artifacts describe a TypeScript-first frontend and idealized Prisma naming, but the live repo differs in two important ways:
  - Frontend feature code is currently JavaScript/JSX, not TS/TSX.
  - Prisma models are currently the introspected snake_case names from the live schema, not a refactored PascalCase model layer.
- For this story, follow the live repo conventions instead of trying to reconcile those differences through broad refactors.

### Quiz Data Contract Notes

- Relevant live Prisma tables and fields:
  - `quiz_templates`: `id`, `code`, `title`, `course_id`, `difficulty`, `question_count`
  - `quiz_questions`: `id`, `quiz_template_id`, `question_type`, `question_text`, `options_json`, `answer_key_json`, `score_weight`
  - `quiz_attempts`: `id`, `user_id`, `quiz_template_id`, `submitted_answers`, `score`, `duration_seconds`, `started_at`, `submitted_at`
  - `courses`: `id`, `code`, `title`, `description`, `level_no`, `duration_hours`
- `generate_quiz` should read from stored templates/questions. Do not fabricate quizzes from loose prompt text while ignoring the training schema already in PostgreSQL.
- `submit_quiz` must persist one attempt row per submission and keep scoring logic on the backend.
- Result payloads sent to the frontend must exclude raw answer keys and any hidden grading internals that are not needed for the user experience.

### Frontend Rendering and Interaction Guardrails

- Reuse the existing structured chat-card pattern from `ChatDashboardPage.jsx` instead of building a separate page-level quiz app.
- Add one new normalized payload type for `quiz`; keep the existing one-message/one-payload model unless the message contract is intentionally expanded.
- Keep quiz interaction state isolated from onboarding checklist state.
- Preserve streaming text behavior so assistant text and quiz cards can coexist in the same message lifecycle.
- Unsupported or malformed quiz payloads must fall back to readable plain text instead of crashing the chat UI.
- Historical quiz messages must rehydrate from persisted metadata when a conversation is reopened from the sidebar.

### Backend and API Guardrails

- Internal generation route should derive identity from `request.internalAgent.userId` only.
- External submission/result routes should derive identity from the authenticated JWT user only.
- Align scope names with the current guard/test vocabulary already present in the repo (`read:training`, `write:training`) unless the catalog proves otherwise.
- Keep controllers thin. Prisma access and scoring logic belong in services.
- Preserve standardized success/error wrappers and `meta.traceId` behavior through the existing global interceptor/filter stack.

### OpenClaw and Tool Guardrails

- There is no existing domain-specific `learning_training_agent` implementation in `openclaw/` yet; the repo currently offers only the generic runtime shell.
- Because generic tool results are sanitized/truncated and normal webchat tool events may omit full result bodies, prefer a narrow backend/orchestrator transformation into the existing chat `uiPayload` contract instead of relying on raw OpenClaw tool event bodies reaching the browser intact.
- Keep quiz payloads compact and deterministic.
- Do not redesign OpenClaw core tool registration or the general plugin architecture in this story unless a very small, strictly necessary hook is unavoidable.

### Cross-Epic Intelligence

- Story 3.3 already established the FE pattern for rendering structured assistant cards inside chat. Reuse that pattern for quiz cards instead of inventing a second rendering model.
- Stories 3.1 and 3.2 already established the backend pattern for thin internal controllers, scoped guards, and service-owned Prisma access. Mirror that pattern for training quiz endpoints.
- Story 4.1 already established the append-only audit/logging path for internal tools. Quiz tool calls must flow through that same path automatically.
